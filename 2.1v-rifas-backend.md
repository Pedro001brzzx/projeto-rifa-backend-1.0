## Ponto 1 — Soft Delete (em vez de hard delete em cascata)

> ✅ **Implementado em 2026-05-07** (Fase B)

**Situação atual:**
`DELETE /api/campanhas/{id}` remove permanentemente a campanha e suas compras associadas. Não há como recuperar o registro após a exclusão.

**Proposta:**
- Adicionar coluna `deleted_at: DateTime` (nullable) nos modelos `Campanha`, `Compra` e `Usuario`
- Filtrar automaticamente registros com `deleted_at IS NOT NULL` em todas as queries públicas
- Endpoint `POST /api/campanhas/{id}/restaurar` (admin) para desfazer a exclusão
- O hard delete permanece disponível como ação explícita separada via query param `?permanente=true`

**Arquivos afetados:**
- `app/models/campanha.py`, `app/models/compra.py`, `app/models/usuario.py`
- `app/routes/campanha_routes.py`, `app/routes/admin_routes.py`
- Migration de banco de dados

**Complexidade:** Média | **Risco de regressão:** Médio

**O que foi feito:**
- Coluna `deleted_at TIMESTAMP NULL` adicionada nos três modelos ✅
- `listar_campanhas` e `obter_campanha_por_slug` filtram `deleted_at IS NULL` ✅
- `listar_titulos_premiados` filtra campanha soft-deletada ✅
- `criar_compra` rejeita campanhas soft-deletadas (404) ✅
- `listar_compras_usuario` filtra `Compra.deleted_at IS NULL` ✅
- `listar_usuarios` e dashboard do admin filtram `Usuario.deleted_at IS NULL` ✅
- `deletar_campanha` virou soft delete por padrão; hard delete via `?permanente=true` ✅
- Nova função `restaurar_campanha` no `campanha_controller.py` ✅
- Novo endpoint `POST /api/campanhas/{campanha_id}/restaurar` (admin, logado) ✅
- Ambas as operações (delete/restaurar) registradas no `AdminLog` via `@with_admin_log` ✅
- Script de migração `scripts/migrate_fase_b.py` para adicionar colunas em produção ✅
- `API_DOCUMENTATION.md` atualizado com comportamento de soft delete, tabela de erros e endpoint de restauração ✅

## Ponto 2 — Proteção Real do Painel Admin

**Situação atual:**
O painel em `/api/painel-secreto-x9/` é protegido pelo JWT + flag `is_admin=True`. A "obscuridade" da URL não constitui segurança real — qualquer vazamento do endpoint a expõe publicamente.

**Proposta:**
- Mover o blueprint admin para `/api/admin/` (URL canônica e documentada)
- Adicionar campo `role: Enum('usuario', 'moderador', 'admin', 'super_admin')` no modelo `Usuario` em substituição ao booleano `is_admin`
- Criar decorator `@requer_role('admin')` genérico no lugar dos checks manuais dispersos
- O campo `is_admin` é mantido por compatibilidade mas passa a ser derivado do campo `role`

**Arquivos afetados:**
- `app/models/usuario.py`
- `app/routes/admin_routes.py` (renomear blueprint e URL prefix)
- Todos os routes que usam verificação manual de `is_admin`
- `swagger.yaml` e `API_DOCUMENTATION.md`
- Migration de banco de dados

**Complexidade:** Média | **Risco de regressão:** Alto

## Ponto 3 — Refresh Token

**Situação atual:**
Access token com validade de 7 dias (`JWT_ACCESS_TOKEN_EXPIRES = timedelta(days=7)`). Quando expira o usuário precisa reautenticar. Não há mecanismo de renovação silenciosa.

**Proposta:**
- Reduzir access token para **30 minutos**
- Emitir junto um **refresh token** com validade de **30 dias** nas respostas de `/api/auth/login` e `/api/auth/registro`
- Novo endpoint `POST /api/auth/refresh` — recebe o refresh token no body, retorna novo access token
- Nova tabela `refresh_tokens`: `(id, usuario_id, token_hash, expira_em, revogado, criado_em)` — permite logout remoto e revogação seletiva por dispositivo
- `POST /api/auth/logout` passa a revogar o refresh token além de invalidar o access token

**Resposta de login após implementação:**
```json
{
  "token": "<access_token>",
  "refresh_token": "<refresh_token>",
  "expires_in": 1800,
  "usuario": { "..." }
}
```

**Arquivos afetados:**
- `app/models/` (novo modelo `RefreshToken`)
- `app/routes/auth_routes.py`
- `app/config.py` (reduzir `JWT_ACCESS_TOKEN_EXPIRES`)
- `swagger.yaml`, `API_DOCUMENTATION.md`
- Migration de banco de dados

**Complexidade:** Alta | **Risco de regressão:** Alto

## Fase E — Adoção de Flask-Migrate (Sistema de Migrations Versionado)

> Data: 2026-05-09 | Status: ✅ **Implementada**

### Contexto e motivação

O projeto hoje usa dois mecanismos ad-hoc para evoluir o schema:

| Mecanismo | O que faz | Problema |
|---|---|---|
| `db.create_all()` em `run.py` e `scripts/init_db.py` | Cria tabelas novas | Não altera tabelas existentes |
| `scripts/migrate_fase_b.py`, `migrate_fase_c.py` | Adicionam colunas individualmente | Manuais, sem rastreio de qual foi aplicada |

**Consequência direta:** em 2026-05-08, as colunas `sorteio_metodo` e `deleted_at` estavam no modelo Python mas ausentes no banco SQLite local — o frontend recebeu 500 em `/api/campanhas` e `/api/ganhadores` até os scripts serem rodados manualmente na sessão de debug.

**Flask-Migrate** (baseado em Alembic) resolve isso: cada mudança de schema vira um arquivo versionado em `migrations/versions/`, aplicado com um único comando e rastreado numa tabela `alembic_version` no próprio banco.

> **Nota:** `Flask-Migrate==4.0.5` e `alembic==1.17.2` **já estão instalados** no venv e declarados em `requirements.txt`. Nenhum `pip install` é necessário.

---

### O que muda

#### Arquivos modificados

| Arquivo | Mudança |
|---|---|
| `app/extensions.py` | Instanciar `Migrate()` e exportar |
| `app/` `__init__.py` | Chamar `migrate.init_app(app, db)` em `create_app()` |
| `run.py` | Remover bloco `db.create_all()` (Migrate assume essa responsabilidade) |
| `Procfile` | Substituir `python scripts/init_db.py` por `flask db upgrade && python scripts/create_admin.py` |
| `scripts/init_db.py` | Remover `db.create_all()`; extrair lógica de criação do admin para `scripts/create_admin.py` |

#### Arquivos criados

| Arquivo | Conteúdo |
|---|---|
| `migrations/` | Diretório gerado por `flask db init` |
| `migrations/env.py` | Configurado para importar todos os modelos |
| `migrations/versions/001_baseline.py` | Migration inicial capturando o schema atual completo |
| `scripts/create_admin.py` | Lógica de criação/atualização do admin extraída de `init_db.py` |

#### Arquivos obsoletos (não deletar — manter para histórico)

- `scripts/migrate_fase_b.py`
- `scripts/migrate_fase_c.py`

### Plano de implementação passo a passo

#### Passo 1 — Registrar Migrate nas extensões

Em `app/extensions.py`, adicionar:
```python
from flask_migrate import Migrate
migrate = Migrate()
```

Em `app/__init__.py`, dentro de `create_app()`, após `db.init_app(app)`:
```python
from app.extensions import migrate
migrate.init_app(app, db)
```

---

#### Passo 2 — Inicializar o repositório de migrations

```bash
flask db init
```

Cria a pasta `migrations/` com `env.py`, `alembic.ini` e `versions/`.

Editar `migrations/env.py` para garantir que todos os modelos sejam importados antes da detecção de mudanças — sem esse import o Alembic não detecta as tabelas:

```python
# migrations/env.py — adicionar após os imports existentes
from app.models import *  # noqa: garante que todos os modelos sejam registrados
```

---

#### Passo 3 — Gerar a migration baseline

```bash
flask db migrate -m "baseline: schema completo v2.1"
```

O Alembic compara os modelos Python com o banco vazio (schema target) e gera um arquivo em `migrations/versions/` com `op.create_table(...)` para cada tabela e coluna existente.

> **Revisar o arquivo gerado** antes de prosseguir — conferir se todas as 10 tabelas aparecem (`campanhas`, `compras`, `usuarios`, `titulos`, `artigos`, `comunicados`, `contatos`, `admin_logs`, `titulos_premiados`, e futuramente `refresh_tokens`).

---

#### Passo 4 — Marcar o banco local existente como já atualizado

O banco `instance/rifas.db` **já tem** o schema correto. Rodar `flask db upgrade` tentaria recriar as tabelas e falharia. A solução é carimbar o banco sem executar a migration:

```bash
flask db stamp head
```

Isso insere o hash da migration atual na tabela `alembic_version` do SQLite, indicando que o banco já está no estado mais recente. A partir daqui, futuras migrations serão aplicadas normalmente com `flask db upgrade`.

> **Banco `instance/app.db`**: arquivo SQLite antigo e obsoleto, pode ser deletado após confirmar que o servidor está funcionando com `rifas.db`.

---

#### Passo 5 — Atualizar `run.py`

Remover o bloco:
```python
# REMOVER:
with app.app_context():
    db.create_all()
```

Em desenvolvimento, o desenvolvedor roda `flask db upgrade` antes de subir o servidor. O `run.py` fica responsável apenas por iniciar o Flask.

---

#### Passo 6 — Separar criação do admin e atualizar o Procfile

Criar `scripts/create_admin.py` com apenas a lógica de upsert do admin (extraída de `init_db.py`).

Atualizar o `Procfile` de:
```
web: python scripts/init_db.py && gunicorn wsgi:app ...
```
Para:
```
release: flask db upgrade
web: python scripts/create_admin.py && gunicorn wsgi:app --workers 2 --threads 2 --timeout 120 --bind 0.0.0.0:$PORT
```

> O comando `release` do Railway executa **antes** do `web` a cada deploy, garantindo que o banco de produção (PostgreSQL) seja migrado antes do servidor subir. Isso elimina a janela de 500 entre deploy e migration manual.

### Workflow após a adoção

#### Adicionar uma coluna nova (ex: Fase C — campo `role` em `Usuario`)

```bash
# 1. Editar o modelo Python
# app/models/usuario.py → adicionar campo role

# 2. Gerar a migration automaticamente
flask db migrate -m "adiciona role em usuarios"

# 3. Revisar o arquivo gerado em migrations/versions/

# 4. Aplicar localmente
flask db upgrade

# 5. Commitar migrations/ junto com o modelo
git add migrations/ app/models/usuario.py
git commit -m "feat: adiciona role em usuarios"

# Em produção (Railway): flask db upgrade roda automaticamente no release
```

#### Verificar o estado atual

```bash
flask db current    # qual migration está aplicada no banco
flask db history    # lista todas as migrations em ordem
flask db heads      # migration mais recente disponível
```

### Tratamento de riscos

| Risco | Mitigação |
|---|---|
| Migration baseline recria tabelas existentes em produção | Usar `flask db stamp head` no banco de produção antes do primeiro `flask db upgrade` |
| Alembic não detecta mudança de tipo em SQLite (limitação do SQLite) | Em produção usa PostgreSQL — sem problema. Localmente, recriar o banco se necessário |
| Developer esquece de commitar o arquivo de migration | CI pode verificar se `flask db check` passa (nenhuma migration pendente) |
| Dois desenvolvedores geram migrations em paralelo | Alembic suporta branching — resolver com `flask db merge` |

### Nota de implementação — 2026-05-09

A migration baseline (`56f40a500000`) foi gerada como **marcador de versão sem ops** (upgrade/downgrade são `pass`). Isso é intencional: o `wsgi.py` já chama `db.create_all()` para bootstrap de tabelas em deploys frescos no Railway, e a migration existe apenas para que o Alembic comece a rastrear o histórico a partir deste ponto. Todas as mudanças de schema daqui para frente serão geradas como migrations normais com `ALTER TABLE`.

**Workflow daqui para frente — adicionar uma coluna nova:**

```bash
# 4. Aplicar localmente
flask db upgrade

# 5. Commitar modelo + migration juntos
git add app/models/ migrations/
git commit -m "feat: ..."
# Railway aplica automaticamente via release: flask db upgrade
```
