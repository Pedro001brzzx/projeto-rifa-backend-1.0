## Ponto 1 — Soft Delete (em vez de hard delete em cascata)

**Situação atual:**
`DELETE /api/campanhas/{id}` remove permanentemente a campanha e suas compras associadas. Não há como recuperar o registro após a exclusão.

**Proposta:**
- Adicionar coluna `deleted_at: DateTime` (nullable) nos modelos `Campanha`, `Compra` e `Usuario`
- Filtrar automaticamente registros com `deleted_at IS NOT NULL` em todas as queries públicas
- Endpoint `POST /api/campanhas/{id}/restaurar` (admin) para desfazer a exclusão
- O hard delete permanece disponível como ação explícita separada via query param `?permanente=true`

**Arquivos afetados:**
- `app/models/campanha.py`, `app/models/compra.py`, `app/models/usuario.py`
- `app/routes/campanha_routes.py`, `app/routes/admin_routes.py`
- Migration de banco de dados

**Complexidade:** Média | **Risco de regressão:** Médio

## Ponto 2 — Proteção Real do Painel Admin

**Situação atual:**
O painel em `/api/painel-secreto-x9/` é protegido pelo JWT + flag `is_admin=True`. A "obscuridade" da URL não constitui segurança real — qualquer vazamento do endpoint a expõe publicamente.

**Proposta:**
- Mover o blueprint admin para `/api/admin/` (URL canônica e documentada)
- Adicionar campo `role: Enum('usuario', 'moderador', 'admin', 'super_admin')` no modelo `Usuario` em substituição ao booleano `is_admin`
- Criar decorator `@requer_role('admin')` genérico no lugar dos checks manuais dispersos
- O campo `is_admin` é mantido por compatibilidade mas passa a ser derivado do campo `role`

**Arquivos afetados:**
- `app/models/usuario.py`
- `app/routes/admin_routes.py` (renomear blueprint e URL prefix)
- Todos os routes que usam verificação manual de `is_admin`
- `swagger.yaml` e `API_DOCUMENTATION.md`
- Migration de banco de dados

**Complexidade:** Média | **Risco de regressão:** Alto

## Ponto 3 — Refresh Token

**Situação atual:**
Access token com validade de 7 dias (`JWT_ACCESS_TOKEN_EXPIRES = timedelta(days=7)`). Quando expira o usuário precisa reautenticar. Não há mecanismo de renovação silenciosa.

**Proposta:**
- Reduzir access token para **30 minutos**
- Emitir junto um **refresh token** com validade de **30 dias** nas respostas de `/api/auth/login` e `/api/auth/registro`
- Novo endpoint `POST /api/auth/refresh` — recebe o refresh token no body, retorna novo access token
- Nova tabela `refresh_tokens`: `(id, usuario_id, token_hash, expira_em, revogado, criado_em)` — permite logout remoto e revogação seletiva por dispositivo
- `POST /api/auth/logout` passa a revogar o refresh token além de invalidar o access token

**Resposta de login após implementação:**
```json
{
  "token": "<access_token>",
  "refresh_token": "<refresh_token>",
  "expires_in": 1800,
  "usuario": { "..." }
}
```

**Arquivos afetados:**
- `app/models/` (novo modelo `RefreshToken`)
- `app/routes/auth_routes.py`
- `app/config.py` (reduzir `JWT_ACCESS_TOKEN_EXPIRES`)
- `swagger.yaml`, `API_DOCUMENTATION.md`
- Migration de banco de dados

**Complexidade:** Alta | **Risco de regressão:** Alto

## Ponto 4 — Expiração de Compra Proativa (Scheduler)

**Situação atual:**
`Compra.expira_em` existe no modelo mas a expiração só é detectada quando a compra é consultada. Compras pendentes acumulam no banco sem serem marcadas como `expirado`, e os títulos reservados nunca são devolvidos à campanha automaticamente.

**Proposta:**
- Adicionar job no APScheduler existente: a cada **5 minutos**, buscar compras com `status_pagamento='pendente'` e `expira_em < utcnow()`, marcá-las como `expirado` e devolver os títulos à campanha (decrementar `titulos_vendidos`)
- Registrar resultado de cada execução no `AdminLog` com a quantidade de compras expiradas
- Novo endpoint `GET /api/admin/compras/expiradas` para consulta administrativa

**Arquivos afetados:**
- `app/scheduler.py`
- `app/routes/admin_routes.py` (novo endpoint)
- `swagger.yaml`

**Complexidade:** Baixa-Média | **Risco de regressão:** Médio

## Ponto 5 — Validação de Schema (Marshmallow)

**Situação atual:**
Validações são feitas manualmente em cada controller (`if not data.get('campo')`). Não há consistência nas mensagens de erro, campos inesperados são silenciosamente ignorados e tipos não são verificados.

**Proposta:**
- Adicionar **Marshmallow** (`marshmallow-sqlalchemy` para integração com SQLAlchemy)
- Criar schemas para cada operação de entrada: `CriarCampanhaSchema`, `CheckoutSchema`, `RegistroSchema`, `LoginSchema`, etc.
- Decorator `@validate_body(SchemaClass)` que injeta os dados validados na view function
- Erros retornam `400` com corpo padronizado:
```json
{
  "erro": "Dados inválidos",
  "campos": {
    "email": ["Não é um endereço de e-mail válido."],
    "titulo": ["Campo obrigatório."]
  }
}
```
- Campos extras na requisição são rejeitados por padrão (`Meta: unknown = RAISE`)

**Schemas estimados (~12):**
`RegistroSchema`, `LoginSchema`, `AtualizarPerfilSchema`, `ResetSenhaSchema`,
`CriarCampanhaSchema`, `AtualizarCampanhaSchema`, `CheckoutSchema`,
`TitulosPremiadosSchema`, `GanhadorSchema`, `ComunicadoSchema`,
`ArtigoSchema`, `ContatoSchema`

**Arquivos afetados:**
- `requirements.txt` (adicionar `marshmallow-sqlalchemy`)
- `app/schemas/` (nova pasta com todos os schemas)
- Todos os controllers de escrita

**Complexidade:** Média-Alta | **Risco de regressão:** Alto

## Ponto 6 — Paginação em `/api/comunicados`

> ✅ **Implementado em 2026-05-03** (Fase A)

**Situação atual:**
`GET /api/comunicados` retorna todos os registros sem paginação. Em produção com volume crescente de comunicados o payload cresce indefinidamente.

**Proposta:**
- Adicionar parâmetros `?page=1&per_page=10` com padrão `per_page=10` e máximo `per_page=50`
- Resposta padronizada igual aos outros endpoints paginados da API:
```json
{
  "comunicados": [...],
  "total": 42,
  "pagina": 1,
  "por_pagina": 10,
  "paginas": 5
}
```
- Aplicar a mesma mudança a `GET /api/artigos` se ainda não tiver paginação

**Arquivos afetados:**
- `app/routes/conteudo_routes.py`
- `tests/test_comunicados.py` (atualizar assertions)
- `swagger.yaml`

**Complexidade:** Baixa | **Risco de regressão:** Baixo

**O que foi feito:**
- Controller `listar_comunicados` já tinha paginação (verificado) ✅
- Route `GET /api/comunicados` já passava `page`/`per_page` (verificado) ✅
- `tests/test_comunicados.py` expandido com 4 novos testes: `test_paginacao_page_e_per_page`, `test_paginacao_per_page_maximo_50`, `test_paginacao_pagina_inexistente` + verificações de `pagina`/`por_pagina` ✅
- `swagger.yaml` atualizado: parâmetros `page`/`per_page` e resposta completa ✅
- `API_DOCUMENTATION.md` atualizado com tabela de parâmetros e exemplo de resposta paginada ✅

## Ponto 7 — Auditoria do Sorteio

> ✅ **Implementado em 2026-05-03** (Fase A)

**Situação atual:**
O modelo `AdminLog` existe mas não está integrado ao endpoint `POST /api/campanhas/{id}/ganhador`. Um admin pode definir qualquer número como ganhador sem deixar rastro auditável. Não há como verificar quem fez o sorteio, quando, ou se o número foi alterado.

**Proposta:**
- Registrar em `AdminLog` toda chamada ao endpoint de ganhador com: admin responsável, `campanha_id`, `numero_sorteado`, `ganhador_id` resultante, IP e timestamp
- Novo endpoint `GET /api/admin/campanhas/{id}/auditoria` retornando o histórico de `AdminLog` filtrado por campanha
- Adicionar campo `sorteio_metodo: Enum('manual', 'automatico')` no modelo `Campanha` para registrar se o número foi definido manualmente pelo admin ou gerado pelo sistema

**Arquivos afetados:**
- `app/routes/ganhador_routes.py` (adicionar registro no AdminLog)
- `app/models/campanha.py` (campo `sorteio_metodo`)
- `app/routes/admin_routes.py` (novo endpoint de auditoria)
- `swagger.yaml`
- Migration de banco de dados

**Complexidade:** Baixa | **Risco de regressão:** Baixo

**O que foi feito:**
- `sorteio_metodo` já existia no modelo `Campanha` (verificado) ✅
- `log_admin_action` já era chamado em `definir_ganhador` com campanha_id, ganhador_id, numero_sorteado e metodo (verificado) ✅
- Novo controller `obter_auditoria_campanha` em `admin_controller.py` com paginação e filtro por `public_id` ✅
- Novo endpoint `GET /api/painel-secreto-x9/campanhas/{campanha_id}/auditoria` em `admin_routes.py` ✅
- `tests/test_auditoria.py` criado com 6 testes: sem auth, usuário comum, campanha inexistente, estrutura da resposta, registro pós-sorteio e paginação ✅
- `swagger.yaml` atualizado com novo endpoint e definição `AdminLog` ✅
- `API_DOCUMENTATION.md` atualizado com documentação completa do endpoint ✅
